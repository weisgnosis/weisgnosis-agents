# Persistent-agent message sharing

`MsgHub.make(Chunk(alice, bob))` installs scoped automatic subscriptions between existing `ReActAgent` runtimes. Each agent retains its own private history and policy. Install `ModelInputTransform.peerAware` on participants to make received observations usable in subsequent model requests. See the complete offline [conversation example](../../../../../../../../../examples/src/main/scala/com/weisgnosis/agents/examples/MsgHubConversation.scala).

The hub starts no agent turn, model request, scheduler or background worker. The host chooses who speaks and when. Observing a reply never broadcasts it again. Closing the owning scope removes this hub's subscriptions and joins admitted deliveries; borrowed agents remain usable.

## Membership and delivery

Creation requires 1–64 distinct participants. `add` is idempotent for current members and does not replay history or announcements. `remove` clears that member's future inbound and outbound subscriptions. Already queued observations remain available; an absent recipient is rejected by flush without deleting its envelope. Explicit re-addition may make it deliverable again. `participants` reads a snapshot, not an execution lease. An agent supports at most 32 hub subscriptions.

`HubMode.Automatic` publishes final responses to current peers, excluding the sender. `HubMode.Manual` disables automatic publication. `setMode` changes future admissions. `broadcast(sender, messages)` explicitly delivers to all current members, including the sender; the sender must be a member. `announce(messages)` delivers host announcements with the hub's identity, without granting System authority in recipients.

Delivery follows membership insertion order. Each overlapping hub is independent and may deliver the same message again; message IDs are not deduplication keys. No shared transcript, history backfill or exactly-once delivery is supplied. Hub operations serialize under one semaphore; cancellation while waiting remains interruptible. Recipient admission never waits for an execution lock. Active or suspended recipients receive Queued receipts and retain observations in this hub until a between-round flush. Duplicate generated envelope identities reject the new observation rather than merging occurrences. The queue admits at most 64 retained messages across all recipients and 1,000,000 encoded characters including envelope identities and payloads; overflow rejects only the new recipient admission. These are retained-data bounds, not total heap or waiting-caller bounds.

## Execution and publication

Final publication occurs after the sender's execution permit and owned execution cleanup are released, before its invocation returns. Ordinary, structured, prepared, streamed and resumed invocations share this boundary. Completed responses and cooperative interruption recovery messages are published. Suspended and Stopped results, failed invocations and genuinely cancelled fibers do not publish a final response.

`AgentResult.peerDeliveries` reports admitted hub/recipient outcomes separately from `AgentRunState`. A missing recipient identifies hub-level rejection. A queued or rejected recipient does not change Completed into failure or trigger another model/tool call. Manual delivery returns the same receipt type. Receipts concern the current payload; delivery first attempts older queued observations to preserve per-recipient FIFO but does not include their receipts in the new batch. `flush` reports those queued attempts explicitly. Already delivered observations remain committed when another recipient rejects. Defects and interruption propagate; abandoning delivery can leave committed observations without returned receipts. Hosts must not retry an uncertain invocation or broadcast automatically.

Lifecycle events and completion observers describe execution before this delivery step. A terminal result-bearing stream value and prepared termination include the returned receipts; event messages are not delivery acknowledgements. The Queued receipt case and new default-empty result field and `peer_observation` content discriminator require rebuilding/upgrading consumers; no frozen binary compatibility is claimed.

`AgentResult` now has a sixth field, `peerDeliveries`. Constructor calls can omit its default, but positional extractors/Product consumers must handle six fields and JVM consumers must rebuild. Older JSON without the field decodes to an empty receipt collection. Older content decoders reject `peer_observation`; upgrade them before exchanging peer history.

## Deferred delivery ownership

Call `hub.flush` after parallel participants finish and before their next round. Queued means retained by the hub, not delivered or consumed by a model. Neither flush nor broadcast starts a participant turn. A suspended participant retains its exact checkpoint and receives queued observations only after it is eligible again. Earlier queued observations prevent later observations overtaking them for the same recipient.

`pendingDeliveries` inspects retained envelopes, including after close. `takePending` atomically transfers and clears them for explicit host handling; transfer is not a delivery acknowledgement or permission to replay an uncertain model invocation. Closing joins admitted hub operations, removes subscriptions and retains pending data for inspection/transfer. It does not wait for suspended agents or start a worker. The host must flush or transfer pending data before discarding the hub handle. This queue is process-local and is not included in agent snapshots.

## Stored observations and verification

Peer messages are retained as inert typed User observations, preserving original content and sender attribution through canonical history/snapshots. Attribution is not authentication. Local call/result occurrence matching remains separate. The [runtime guide](../agent/README.md#passive-peer-context) explains bounds, request projection, media and transcript/memory limits.

## Explicit pipelines

`Pipeline.sequential(agents, input)` invokes 1–64 distinct persistent runtimes in declaration order. It returns attributed `StageResult` values through the first non-Completed result, preserving the full result and any suspension checkpoint. Later stages receive only the previous completed reply as an inert attributed User observation. Install `ModelInputTransform.peerAware` on those stages; the pipeline does not replace their policies or request transforms. Private histories and local tool ledgers remain separate. Typed execution failures propagate and already executed stages are not rolled back or retried.

`Pipeline.fanout(agents, input, parallelism)` supplies the same immutable input to distinct runtimes, with an explicit concurrency limit of 1–64. Returned `StageOutcome` values follow declaration order, regardless of completion order. Ordinary typed failures and all successful run states remain per-stage data. Defects and interruption fail the operation after owned children and their cleanup are joined; caller cancellation never becomes a successful result collection.

These functions borrow agents and close each stage's invocation scope before returning or handing off. They install no hub subscriptions, shared history, workflow graph, scheduler, retry policy or persisted pipeline continuation. Existing agent subscriptions still have their ordinary behavior. After fanout with an automatic hub, call `hub.flush` before the next round so deferred peer observations arrive. Sequential handoff already carries the previous reply; using automatic hub publication as well can retain that reply twice, so select Manual mode or use one delivery route. A host that needs resume must retain the actual non-Completed result and choose an explicit next operation.
